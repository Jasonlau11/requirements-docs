## 0. 摘要

当前订单系统只有一种报名表单：接单方在报名弹窗里填一段自由文本（前端叫「报名说明」，接口字段是 `Enrollment.proposal`）。发单方无法据此向不同接单方索取结构化信息（例如"请选择你可接受的交付周期"、"请勾选你具备的技能"）。

本方案引入**两套并行的报名模式**，由发单方在发布时选择：

- **默认模式（现状）**：只填一段报名说明，行为与今天完全一致；
- **自定义问卷模式**：发单方自行配置题目，接单方按题目逐项作答后报名。支持四种题型：**多行文本（≤2000 字）**、**单选**、**多选**、**纯说明字段（无输入，仅展示）**。

三条核心约束：

1. **模式与题目在订单首次上架后永久不可修改**（判定条件 `Order.approvedAt != null`，该时间戳在代码中只写一次、从不回填为空）。上架前订单对报名者完全不可见，改动不产生任何冲突；上架后订单一律不可编辑，问卷只是并入这条既有规则，并顺带覆盖了"下架/隐藏 → 待上架"这个唯一还能改单的窗口。
2. **问卷模式与"报名说明"互斥**：选择问卷模式后不再展示、不再要求报名说明，避免同一份报名信息出现两个真源。
3. **答案提交后不可修改**，需要修改只能撤回报名后重新报名（这是现有模型，本方案不新增更新入口）。

## 1. 背景与现状

### 1.1 问题现象

所有公开抢单订单的报名表单完全一样：一段 20 字起步的自由文本。发单方想按自己的订单要求收集信息（预算区间对应的交付承诺、可接受的结算方式、技能勾选、必读的注意事项）只能靠接单方自由发挥，无法结构化比较，也无法在名单里筛选。

### 1.2 现状链路（代码级）

#### 发单侧（三条写入路径，最终都落到 `Order` 聚合）

| 路径 | 入口 | 说明 |
|---|---|---|
| Web 手动发布 | `POST /api/v1/orders/draft` → `OrderAppService.reviseOrderDraftForCurrentCustomer` → `Order.reviseDraft(OrderDraftRevision)` | 新建与编辑共用。前端 `OrderPublishPage` 以"保存草稿 + 提交审核"两步提交；待上架态下会自动保存 |
| MCP 发单 | `POST /api/v1/mcp/orders`（`McpWriteController.mcpCreateOrder`）→ `createAndSubmitOrderForCurrentCustomer` | 创建即提交，原子进入 PENDING_REVIEW |
| AI 发单 | `POST /api/v1/ai-orders/confirm-and-submit`、`POST /api/v1/ai-advisor/sessions/{id}/publish` | 由骨架模块/草稿生成订单，字段集与上面两条不同 |

可编辑窗口（`Order.canModify()`，`opcs-domain/.../aggregate/Order.java:1185-1197`）：

- `DRAFT`、`REJECTED`：可编辑；
- `PENDING_REVIEW`：可编辑，保存修订后**回退为 `DRAFT`**（`Order.java:1294-1298`）——前端对"待审核"订单提供「修改订单」按钮（`opcs-order-front/src/app/components/order-detail-actions.ts:52-54`）；
- **待上架态** `isPendingRelist()`（`PROMOTING` + `OPEN_BIDDING` + `listingStatus=1` + 未选标）：可编辑并可重新上架 —— 这是全流程中**唯一"订单曾经上架、且还能改内容"的窗口**；
- 已上架（`PROMOTING` + `listingStatus=2`）：内容字段全部不可编辑，唯一例外是「调整报名时限」（`Order.java:493-510`）。

进入待上架态的两条现实路径：客户对已上架的公开单点「下架订单」（前端是取消按钮，后端 `OrderAppService.cancelOrderForCurrentCustomer:463-465` 判到 `isListedOpenBidding()` 时转为下架），以及调度器超时下架/超时隐藏（`OrderTimeoutScheduler.java:44,73`）。

### 1.3 关键约束（本方案成立的依据）

1. **报名只可能发生在已上架的公开抢单订单上**。因此"订单未上架"与"存在报名数据"是互斥的：`DRAFT` / `PENDING_REVIEW` / `REJECTED` 阶段无论如何改问卷，都不可能和任何人的作答冲突。
2. **唯一"既有报名、又能改单"的窗口是待上架态**。`relist()` 会把暂挂报名恢复为有效报名并保留原报价与原方案（`Order.java:625-653`、`Enrollment.restoreForRelist`）——如果允许在这个窗口改问卷，暂挂报名恢复后就会带着与当前题目对不上的旧答案。
3. **`Order.approvedAt` 只写一次且从不清空**（`Order.java:433` 赋值，全库无清空点），是可靠的"是否上架过"标记。相比之下 `submittedAt` 会被清空（`Order.java:363`、`:1297`），不能用来做永久锁。
4. **t_order / t_enrollment 没有裸 SQL 插入**（全仓无 `INSERT INTO t_order` / `INSERT INTO t_enrollment`，写入统一走 MyBatis-Plus 的 PO），加列只需改 PO。
5. 迁移版本当前最高为 **V106**，新迁移用 **V107**（V100 缺失是既有情况，Flyway 允许）。

## 2. 目标与非目标

### 目标

1. 发单方在发布公开抢单订单时，可选择"默认报名说明"或"自定义问卷"，并配置题目；
2. 支持四种题型：多行文本（≤2000 字）、单选、多选、纯说明字段；
3. 接单方在报名时按题目作答，必填项未填不允许提交；
4. 发单方能在报名名单中看到每位接单方的作答，并能随名单一起导出；
5. MCP 侧具备同等能力（配置题目、提交作答、读取作答）；
6. 历史订单与历史报名数据行为零变化。

### 非目标

- 不支持条件跳题、矩阵题、附件题、评分题等复杂题型；
- 不支持答案修改（只支持撤回后重新报名）；
- 不支持报名后的答案用于自动分配/综合评分（`OrderAllocationAppService` 仍只用报价与报名时间）；
- 不支持 AI 发单两条链路配置问卷（v1 落默认模式，见决策 D6）；
- 不改动报名人数口径（仍是 `ENROLLED + OFF_SHELF`）。

## 3. 已确认的决策

### D1 冻结口径：首次上架后永久不可修改（`approvedAt != null`）

**决策**：订单一旦被运营审核通过并上架（`approvedAt` 被写入），报名模式与题目即永久锁定，任何路径都不得修改。

**为什么不是"提交审核时锁定"**：提交审核到上架之间，订单对报名者完全不可见（报名要求 `listingStatus=2`），此阶段改问卷不可能与任何数据冲突。提前锁在提交时会砍掉两条既有业务流程：①待审核撤回修改（前端有「修改订单」按钮，后端保存修订会退回 `DRAFT`）；②运营驳回返修（`REJECTED` 状态的存在意义就是让发单方改完重提）。若运营驳回理由恰是"问卷题目表述不清"，锁在提交时会变成整单删除重建，把运营审核变成单向门。

**为什么不是"有报名时才锁定"**：那样判定条件需要判断"新旧问卷是否等价"（题目 id、选项顺序、空白符任何一点往返差异都会让待上架期的自动保存误报），而且需要一个可重入的解锁判定；用 `approvedAt` 是一个现成时间戳，判定是一行代码，前端只需按服务端下发的只读标志渲染。

**已知代价（可接受）**：订单上架过、一个报名都没有、被下架之后，发单方不能再调整问卷。此情形下的替代手段是新建订单。

### D2 双模式并行，历史订单默认落默认模式

新增 `enrollment_form_mode`：`1 = 默认报名说明`（历史值与默认值）、`2 = 自定义问卷`。所有已有订单不需要回填，读取到 `1` 即走现状逻辑。

### D3 问卷只在公开抢单（OPEN_BIDDING）可配置

因为报名入口只存在于公开抢单订单（见 1.3）。发单页在选择"指定接单方 / 运营指派 / 推荐推送"时不展示问卷配置区；服务端在 `mode=2` 且 `acceptanceMode != OPEN_BIDDING` 时直接拒绝保存（`DomainException`），避免配置了却无人填写的空转。

### D4 题目标识使用不透明 id，禁止用题目文案派生字段名

题目 id 一律为 `q1..qn`（服务端生成，客户端不可自定义）。原因有两条：①MCP 侧的脱敏器是按**字段名**匹配的（`opcs-order-mcp/src/tools/third-batch-handlers.ts:49-71`，命中 `phone/email/wechat/fileurl` 等片段即整字段剔除），若用题目标签派生 key（例如 `contact_phone`），答案会从发单方在 MCP 看到的名单里凭空消失；②题目文案可改可重名，做 key 不稳定。

### D5 答案提交后不可修改

沿用现有模型：没有报名更新接口，要改只能撤回（`DELETE /api/v1/enrollments/{id}`）后重新报名。

**已知影响（需在方案中留痕）**：撤回再报名会新插一行、报名时间重置，因此会影响按 `created_desc` 的排序、以及"综合分/先到先得"两种自动分配策略（`OrderAllocationAppService`）。客服话术需相应说明。

### D6 AI 发单两条链路不支持问卷（v1）

`CreateOrderFromAiRequest` / advisor `publish_plan` 生成的订单落默认模式。理由：AI 路径的字段由骨架模块推导，问卷属于强产品配置，让模型生成题目风险高于收益。后续如需支持，建议走"AI 生成草稿 → 发布页人工确认问卷"的路径，而不是直接进 `publish`。

### D7 问卷模式下报名说明字段被替换（不再展示、不再必填）

服务端在 `mode=2` 时不再要求 `proposal`，前端也不再展示该输入框。为兼容老客户端，后端仍接受 `proposal` 写入（不报错），但不参与展示——真正的强制点是**答案**：`mode=2` 且 `answers` 缺失或不合格时，报名一律拒绝并返回明确业务码（见 4.4）。

## 4. 方案设计

### 4.1 数据模型

#### `t_order` 新增两列

| 列 | 类型 | 说明 |
|---|---|---|
| `enrollment_form_mode` | `TINYINT NOT NULL DEFAULT 1` | `1` 默认报名说明（历史值），`2` 自定义问卷 |
| `enrollment_questions` | `JSON NULL` | 问卷定义，结构见附录 C。`mode=1` 时为 `NULL` |

选择 JSON 列而不是子表：定义随订单整体读写、不按字段检索，与既有 `t_order.order_tags` / `task_type_codes` 同一模式（V35 已在本表使用 JSON，MySQL 5.7+ 前提已成立）。

#### `t_enrollment` 新增两列

| 列 | 类型 | 说明 |
|---|---|---|
| `answers` | `JSON NULL` | 作答，按题目 id 键值，结构见附录 C。默认模式订单为 `NULL` |
| `form_hash` | `VARCHAR(64) NULL` | 提交时问卷定义的 SHA-256。**仅作异常检测**（见下），不参与渲染 |

**关于 `form_hash`（保险而非必需）**：D1 的冻结规则保证了同一订单的问卷定义唯一，因此名单与导出都以**订单当前定义**为权威来解析答案，不需要按行解析快照。`form_hash` 只用于兜底：万一出现数据订正、代码回滚或人工改库导致定义与作答不一致，可以检测出来并降级为"原始键值"展示，而不是静默错位。这正是"锁定是产品规则、快照是数据完整性"的分工。

### 4.2 领域层改动

#### `opcs-domain/.../order/valueobject/EnrollmentQuestionnaire.java`（新增）

问卷定义的值对象，负责**自校验**（构造即校验，非法直接抛 `DomainException`）：

- 题目数 `1..20`；
- 每题 `title` 非空且 `≤100` 字；
- `TEXT`：`maxLength` 默认并上限 `2000`；
- `SINGLE`：选项 `2..20`，选项 `key` 唯一、`label` 非空且 `≤200` 字；
- `MULTI`：同 `SINGLE`，且 `1 ≤ minSelect ≤ maxSelect ≤ 选项数`；
- `NOTE`：只有 `title` 与 `content`（`≤2000` 字），**不允许 `required`**，也不接受作答。

同时提供 `validateAnswers(Map<String, Object> answers)`，供报名侧复用。

#### `opcs-domain/.../order/aggregate/Order.java`

新增字段 `enrollmentFormMode`、`enrollmentQuestions`（`EnrollmentQuestionnaire`）：

- `create(...)`：接收两个新参数（**带默认值**，避免打断 MCP/AI 两条构造路径）；
- `reconstitute(...)`：从 PO 还原；
- **`reviseDraft(revision, customerId)`（`:1211-1300`）新增冻结判断**：
  ```java
  // 首次上架后问卷永久锁定：以库中值为权威，忽略修订里的问卷字段
  if (approvedAt == null) {
      this.enrollmentFormMode = revision.getEnrollmentFormMode();
      this.enrollmentQuestions = revision.getEnrollmentQuestions();
  } else if (revisionCarriesQuestionnaireChange(revision)) {
      log.warn("订单已上架，忽略问卷修订 orderId={}", orderId);
  }
  ```
  这里刻意选择**忽略**而不是**报错**：待上架态前端会自动保存修订，任何往返差异（字段缺失、顺序变化）都不应打断自动保存；真正的门控是前端只读 + 服务端库中值为权威。这样旧版前端（不认识问卷字段）提交的修订也不会清空定义——这一点很关键，因为后端 `reviseDraft` 对 `null` 的既有语义是"清空"（`taskTypeCodes`、`skeletonModules` 都是如此），问卷字段必须显式豁免。
- 新增只读派生方法 `isEnrollmentFormLocked()`（`return approvedAt != null;`），供 DTO 下发。
- `addEnrollment(...)`：`mode=2` 时校验 `answers`（复用 `EnrollmentQuestionnaire.validateAnswers`），并把 `form_hash` 写到报名记录上。

#### `opcs-domain/.../order/entity/Enrollment.java`

新增 `answers`（原始 JSON）与 `formHash`；`create(...)` / `restore(...)` 增加参数；其余状态行为（`suspendForOffShelf` / `restoreForRelist` / `select` / `markNotSelected`）**不需要任何改动**——答案随行保留，下架暂挂与重新上架天然带着答案往返。

## 6. 部署上线顺序

### 6.1 时间线

1. **后端**（含 V107 迁移）：新字段可选、默认模式，此时线上行为零变化；
2. **前端**：发布页与报名弹窗上线，功能自此对用户可见；
3. **MCP**：`pnpm openapi:update` 重拉快照 → 改 tool schema 与 handler → 发布；
4. **（可选）运营审核展示**：与步骤 2 同批或紧随其后。

### 6.2 为什么是这个顺序

MCP 与前端的生成式 API 客户端都以后端 OpenAPI 为准；后端先上且保持纯增量（只加可选字段），任何一步单独回滚都不会造成契约断裂。MCP 放最后是因为它需要重新快照并对齐 tool schema，且外部 agent 的失败模式（老客户端拿业务码）需要在后端已支持答案校验之后才能验证。

### 6.3 回滚预案

- 迁移只加列，**不需要**回滚 DDL（`enrollment_questions`/`answers` 留空无害）；
- 代码回滚（前端回退）：已产生的 `mode=2` 订单在旧前端会显示为"没有题目"的报名页，已提交的答案在旧名单弹窗里不可见（数据仍在库中）。因此**回滚前应先确认没有正在进行的问卷模式订单**，或先把这些订单下架；
- 后端回滚同理：`mode=2` 的订单会退回"只认 proposal"的行为，此时新报名会被拒绝（`proposal` 未提交）——所以后端回滚前也应先下架问卷模式订单。

### 6.4 上线后 smoke check

1. 默认模式下单 → 提交 → 运营通过 → 报名：流程与线上一致（回归）；
2. 问卷模式下单（含四种题型各一题，纯说明字段放中间）→ 提交 → 通过 → 待上架态检查问卷已锁（编辑器只读，且保存修订不会改变定义）；
3. 接单方报名：必填漏填被拦、文本题 2000 字边界、多选数量边界、未知题目 id 被拒；
4. 发单方名单弹窗与 xlsx 导出：题目列顺序与定义一致，多选合并展示正确；
5. 下架 → 重新上架：答案完整保留；
6. MCP：`create_order` 带问卷 → `get_order_detail` 能看到定义 → `bid_order` 带 `answers` 成功；不带 `answers` 返回 `ENROLLMENT_ANSWERS_REQUIRED`。

```sql
-- 列是否就位
SELECT table_name, column_name, column_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = DATABASE()
  AND ((table_name = 't_order'      AND column_name IN ('enrollment_form_mode','enrollment_questions'))
    OR (table_name = 't_enrollment' AND column_name IN ('answers','form_hash')));

-- 历史数据应全部为默认模式
SELECT enrollment_form_mode, COUNT(*) FROM t_order GROUP BY enrollment_form_mode;

SELECT id, order_no, acceptance_mode, enrollment_form_mode

LIMIT 50;
```

题型枚举：`TEXT`（多行文本）、`SINGLE`（单选）、`MULTI`（多选）、`NOTE`（纯说明，无输入、不参与必填与作答）。

### C.2 作答（`t_enrollment.answers`）


约定：`SINGLE` 存选项 `key`（字符串），`MULTI` 存 `key` 数组，`TEXT` 存原文，`NOTE` 不出现。
